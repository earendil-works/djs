## Owner
"One potentially quite nice aspect of how we do the builtins is that it should be possible
to build a JIT that emits more wasm. Investigate this, both in terms of performance and
whether it makes sense for our setup."

## Context
- Builtins are written once in a TypeScript subset; bgen compiles them to bytecode (every
  builtin) and optionally to resumable Rust state machines (`@native`, D1632), i.e.
  already an ahead-of-time "compile to wasm" path, used sparingly because of module size.
- G5 suspend anywhere: execution stops at any instruction, frames live in the heap, fuel
  counts work deterministically, snapshots are images. Determinism and fuel must hold.
- wasm module budget (D020), per-VM memory (0151), one VM per wasm instance in pi.
- pico (docs being studied in 0152, work/scratch/0152/pico-docs.txt "The JIT" and
  docs/jit.md references) has a JIT in its wasm VM: read what it does and measures.

## Questions
1. **Options**, each with what it compiles and when:
   a. AOT: builtins (all or hot) compiled to wasm at build time from bgen output (more
      `@native`-like code, or a new bgen wasm backend), shipped in the module or as a
      separate, lazily loaded module;
   b. runtime JIT of user code (and/or builtins) to wasm: the engine emits wasm bytes for
      hot functions, the host compiles them (`new WebAssembly.Module`), instantiates them
      against the same memory/table/imports, and the interpreter calls into them via a
      table; Liftoff vs TurboFan costs in V8; browsers/Node/other hosts (wasmtime?).
   c. baseline template JIT (bytecode -> straight-line wasm per function, no
      speculation) vs an optimizing tier (types from ICs, guards, deopt to the
      interpreter).
2. **Fit with djs's invariants**: suspension at any instruction from JIT code (spill to
   the heap frame at safepoints, resume in the interpreter or re-enter compiled code at a
   resume point), fuel accounting identical to the interpreter (determinism D1680 etc.),
   GC interaction (moving collector: JIT code must not hold raw offsets across
   safepoints), snapshots (compiled code never in images; recompiled after restore),
   no_std/no-unsafe djs-core (the emitter is plain byte writing; the host does the rest),
   the wasm ABI (a host import for "compile this module"?), security (the code is
   generated by us from verified bytecode).
3. **Performance**: where does djs spend time on the workloads and pi-like (interpreter
   dispatch vs builtins vs GC vs host calls), and what fraction a JIT could remove;
   compile latency vs codemode scripts' typical runtime (short scripts, mostly waiting on
   tools); a **prototype**: a template compiler for a small bytecode subset (e.g. a numeric
   loop and property access) emitting wasm, compiled and called from node, measured
   against the interpreter (wall time and V8 compile time), in scratch.
4. **Cost**: engine code size added to the module, per-VM memory, complexity and risk,
   test strategy (the interpreter as the oracle; differential runs; stress modes).
5. **Recommendation** for djs: do / don't / which variant first, with numbers.

## Deliverable
docs/wasm-jit.md with the prototype numbers.

## Log
- Read ARCH (G5, interpreter, builtins, fuel), TESTING (instruction ratios), the guide's
  interpreter/builtins pages, scripts/perf, pico's "The JIT" chapter and benchmarks, and
  docs/lessons-from-pico.md (0152).
- Profiles: node --cpu-prof of the wasm workloads, bucketed (work/scratch/0153/prof).
  pi-like: run_hot 12%, interpreter total 22%; calls 94%; json 3%.
- Real scripts: the 300 codemode-harvest scripts in djs-wasm: median 0.12 ms / ~3,000
  fuel, p99 1.4 ms / ~95,000 (work/scratch/0153/harvest).
- @native vs bytecode backend: pi-like 0.09 vs 0.30 s natively (the existing AOT path).
- Prototype (work/scratch/0153/proto, kept on branch scratch/0153-wasm-jit-proto): a
  template compiler for 26 opcodes of real djs bytecode (parsed from `djs disasm`), in a
  miniature of djs's memory model, with block-batched exact fuel, exits at instruction
  boundaries, write-back, nested compiled calls and re-entry at block leaders. The
  interpreter oracle passes 60/60 runs (5 programs x slices 7/97/1000/1e9 x 3 variants);
  two injected bugs are caught.
- Numbers: TurboFan code 3.2-4.5x djs's interpreter on loops/calls (7.9x on a simplified
  property cache), exact fuel 4-14%, Liftoff-only 0.7-1.8x; V8 compile: lazy module
  ~0.03 ms + Liftoff 0.01-0.04 ms per function, TurboFan 0.3-1.9 ms per function
  (0.5-1 ms/KB), 1.4 MB function: TurboFan zone OOM; break-even 10^4-10^5 iterations.
- instr.py (scripts/perf) no longer patches gc.rs (mark_compact is wrapped in
  without_barrier now); a fixed copy in scratch built, but its fast-path counters no
  longer match run_hot either, so its user/prelude split was not used.
- Wrote docs/wasm-jit.md and D2510 (no JIT; AOT stays @native). No guide pages affected
  (guide: -). The bytecode-encoding change of 0151 (L4) does not affect the prototype (it
  reads the disassembly) and would only touch a real JIT's decoder.

## Follow-ups
- scripts/perf/instr.py is stale: its gc.rs patch fails (mark_compact now runs inside
  `without_barrier`) and its fast-path counters show 0 prelude bytecodes / 100% slow
  path, so the run_hot patch no longer matches either.
- If images should ever be compared byte for byte across execution modes (a JIT, or any
  tier that keeps operands out of memory), suspension or the image writer must clear the
  value-stack slots above `sp` (safepoint_collect already does before a collection).
