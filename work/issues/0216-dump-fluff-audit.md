## Goal
Owner: the dump work is not done until dumps are the absolute smallest possible (no fluff)
and dump performance is the fastest possible. This issue defines "smallest possible" concretely
so 0207 (pjs) and follow-ups have a complete queue.

For a representative set (examples/sleep-dump; the pi suite's median and largest dumps; the
v2 programs with the largest dumps; corpus classes: data-heavy, many closures, loops, classes,
generators, Promise.all), write by hand the **byte-minimal dump** that:
- continues the run exactly (djs and node), with the same host interface ($djs.seed, resume,
  host, source, the runtime helpers; D2834-D2836, D2970-D2973);
- can still be dumped again (whatever minimal information re-dump needs; challenge every field
  of the current records, including 0207 item 4's planned `{f, at, h, r}`);
- keeps the user's own code text as written (no minifying of their code), but treats every
  generated byte as negotiable: names (`$dump.n2`, `$djs_i1`), `globalThis.$dump = {}`, the
  header and "use strict", the seed line when Math.random was never used, the `$djs.k(` wrapper,
  the final try/finally, single-use values, temporaries, parentheses, whitespace, record
  encodings, data encodings (arrays, objects, strings, numbers, shared structure).
Then diff each against the current exporter's output (main), byte by byte: every difference
gets a category, its size (raw and gzip), why the exporter writes it, whether it is removable,
how, and at what cost (complexity, exactness, readability). Note any difference that depends on
an owner decision (e.g. shortening generated names, dropping readability) separately.

Output: work/research/0216/README.md with the minimal dumps, the per-byte accounting, totals
(current vs minimal, raw and gzip, per set), and a ranked queue of changes with expected savings.
Send the coordinator a short summary. Do not edit exporter code (pjs owns it for 0207).
