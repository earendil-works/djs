## Goal
ARCH P2 exit criterion: "pi codemode runs on djs behind a flag". pi-private is another
repo and we do not modify it here. This issue builds everything on our side and shows
that it works:

- `~/Development/pi-private/packages/codemode/src/runtime/vm.ts` runs codemode on
  quickjs-wasi: it evaluates `PRELUDE_SOURCE` (prelude-source.ts), wraps the script as
  `(async (tools, console) => {code\n})`, handles tool calls, store/load, text/image
  output, fuel/deadlines, and snapshots ("drepl"-style durability?). Read it, and
  execution.ts/host.ts/protocol.ts, fully.
- Build `js/pi/` (or similar): a djs-backed implementation of the same VM-session
  contract that vm.ts implements, on top of `js/src/sandbox.ts`, running pi's real
  PRELUDE_SOURCE (imported read-only from pi-private, or copied into a fixture with the
  pi commit noted).
- Run pi's codemode tests (packages/codemode/test/*.test.ts) against it where that is
  possible without modifying pi-private (for example a copy of the test files with the
  import redirected, generated by a script so it can be refreshed), and report which
  pass and which fail, and why.

## Acceptance criteria
- [ ] A written comparison of pi's VM contract with what djs provides (docs/host.md "pi"
      section): the matches, the gaps, and what pi would need to change to use djs
      behind a flag. That is the input for the owner's decision on the actual pi
      integration.
- [ ] The adapter, with tests in this repo (node --test), running representative
      codemode scripts: tool calls (concurrent), store/load, text/image output, errors,
      fuel exhaustion, snapshots, and Date/Math.random determinism if pi relies on it
      ("deterministic" in vm.ts).
- [ ] pi's own tests run against the adapter: pass/fail per test with reasons.
- [ ] Performance: script start and a typical tool-heavy script, djs vs quickjs-wasi in
      node (if quickjs-wasi is installed in pi-private's node_modules, use it read-only).
