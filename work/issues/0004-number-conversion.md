## Goal
Correct and fast number formatting and parsing for the engine, without dependencies
(ARCH.md "Crate / Repo Layout": we write our own Ryu-style shortest formatting and
Eisel-Lemire parsing). Output must match QuickJS (`qjs`) exactly.

## Acceptance criteria
- [x] `Number::prototype.toString()` / `ToString(Number)`: shortest round-trip digits
      (Ryu or an equivalent proven algorithm) plus the spec's formatting rules (exponent
      thresholds at 1e21 and 1e-7, `-0` gives `"0"`, `NaN`, `Infinity`).
- [x] `toString(radix)` for radix 2..36, including non-integers, matching qjs output.
- [x] `toFixed`, `toExponential`, `toPrecision` with exact decimal digits (they need
      arbitrary precision for large or small values; a small internal bignum is
      expected), matching qjs including the range checks (the RangeError conditions are
      reported to the caller as an error enum, not thrown).
- [x] `StringToNumber` (the `Number(str)` grammar): whitespace and line terminator
      trimming, `Infinity`, `0x`/`0o`/`0b`, empty string gives 0, invalid gives NaN.
      Correctly rounded decimal parsing: Eisel-Lemire with a correct slow-path fallback
      (big decimal).
- [x] `parseFloat` prefix semantics and `parseInt(str, radix)` helpers.
- [x] Numeric literal values: a function the compiler will call with a literal's digits
      (decimal, hex, octal, binary, separators already validated by the lexer). Accept
      the raw bytes with `_` separators and skip them.
- [x] Input as `&[u8]` (Latin-1/ASCII) and `&[u16]` (two-byte strings), or one generic
      path over both. Output into a caller-provided buffer or a small stack buffer; no
      allocation on the common paths.
- [x] Tests: unit tests for edge cases (subnormals, powers of ten, halfway cases, max/min
      values, `-0`). Large randomized round-trip tests against Rust's std (`f64` parse /
      `{}` / `{:e}`). A checked-in corpus under `tests/data/num/` of several thousand
      inputs with qjs's output for every operation (generated by a script that runs
      `~/Development/dquickts/qjs`; check in the script too), compared in a unit test.
- [x] Rough performance numbers in the Log (formatting and parsing ns/op, native).

## Notes
- `no_std`, no dependencies. Use only `core`; `libm` is not needed here.
- Reference: QuickJS `dtoa.c` (in `~/Development/dquickts`, read-only) shows the exact
  qjs behavior for radix and fixed/precision formatting. Ryu: Ulf Adams, PLDI 2018.
  Eisel-Lemire: as in Rust's `core::num::dec2flt` (you may port that approach; note the
  license, MIT/Apache, which is compatible).
- Code size matters for wasm (ARCH G2). Prefer compact tables, for example the Ryu small
  table variant or computing powers on the fly. Record the table sizes in the Log.

## Log

2026-11-01 (num)
- Read dquickts' `dtoa.c` and the number paths in `quickjs.c` (js_atof, js_dtoa2, the
  Number.prototype methods, parseInt/parseFloat, skip_spaces/lre_is_space) to pin down qjs
  behavior. Checked edge cases against `qjs` directly (whitespace set: U+0085 and U+180E are
  not whitespace, `+0x10` is NaN for Number but 16 for parseInt, `parseInt("0x", 16)` is NaN).
- `num/big.rs`: fixed-capacity bignum (100 u32 limbs = 400 bytes on the stack), only small
  multiply/divide, pow, shifts with sticky bit. Capacity bounds documented per user.
- `num/pow5.rs`: one canonical table C(q) = floor(5^q normalized to 128 bits), q in
  -342..=325, stored as every 27th value plus 2-bit corrections. Both Ryu's tables (125-bit
  split and inverse split) and the Eisel-Lemire table are derived from it exactly. Tests
  rebuild all 668 entries with the bignum and check Ryu's and Lemire's own definitions; a
  one-off diff against Rust core's `dec2flt/table.rs` showed all 651 Lemire entries identical.
  **Table sizes:** 26 x u128 base (416 B) + 27 x u64 powers of 5 (216 B) + 42 x u32
  corrections (168 B) = 800 B, plus 23 f64 (184 B) for Clinger's fast path and three 35-byte /
  140-byte radix tables from qjs (DTOA_MAX_DIGITS, MUL_LOG2_RADIX).
- `num/ryu.rs`: Ryu d2d ported from the `ryu` crate. `num/exact.rs`: exact
  round(x * 2^e * radix^k) to integer (half-even or half-up) and to f64.
- `num/format.rs`: to_string (integer fast path, Ryu, JS layout), to_string_radix (qjs'
  shortest search for radix != 10, never exponential), to_fixed/to_exponential/to_precision
  (exact, half-up, qjs check order: e.g. toFixed range check before NaN, toExponential/
  toPrecision return ToString for non-finite before the range check).
- `num/parse.rs`: generic over u8/u16. Decimal: scan, Clinger fast path (incl. "disguised"),
  Eisel-Lemire (with the w+1 check for > 19 digits), exact slow path keeping 800 significant
  digits plus a sticky bit. Power-of-two radixes exact; other radixes as qjs (truncate to 128
  bits of digits). StringToNumber, parseFloat, parseInt, literal_value.
- Found one intentional deviation from qjs: qjs truncates decimal input after 38 significant
  digits (not correctly rounded); we round correctly like V8 (D1041).
- Note: Rust's `{:e}` and the spec disagree when the exact value is exactly halfway between two
  shortest candidates (e.g. 1658206780088562.25): the spec (and Ryu, and qjs) pick the even
  digit; the randomized test accounts for that.
- Tests (26 unit tests, ~5 s in debug): edge cases; 300k random doubles vs std `{:e}` + round
  trip; 300k random decimal strings + 900k printed doubles vs std parse (Number, parseFloat,
  literal); 60k random toFixed/toExponential/toPrecision vs a reference built from Rust's exact
  decimal expansion and the spec text; radix round trips; slow path and Lemire directly vs std
  (200k); qjs-style radix search vs Ryu in base 10 (100k); u8 and u16 inputs always compared.
- qjs corpus: `tests/data/num/gen-corpus.js` (+ `gen-corpus.sh`) writes `corpus.txt` (26,341
  cases, 1.4 MB, 316 KB gzipped): String, toString(radix), toFixed, toExponential, toPrecision
  (incl. RangeErrors) for 2,500 doubles; Number, parseFloat, parseInt for 3,000 strings plus
  1,000 parseInt digit strings. All match. The script also takes `SEED SCALE`; four extra runs
  with scale 20 (2.1M cases, not checked in, via the ignored `qjs_corpus_external` test) all
  matched as well. Decimal inputs in the corpus stay at <= 36 significant digits (D1041).
- **Performance** (native, release, Apple M-series, `bench_conversions` ignored test):
  to_string: int 6 ns, short decimal 30 ns, random double 32 ns (std `{}`: 50 ns);
  toFixed(2) 34 ns; toPrecision(6) 145 ns; toString(16) of random doubles 100 ns.
  string_to_number: int 6 ns, short decimal 7 ns, 17-digit shortest output 25 ns (std parse:
  13 ns), 31 digits 68 ns, UTF-16 17-digit 26 ns. The first scanner version (per-digit
  significant-digit counting) was 33 ns for scanning alone; accumulating with wrapping
  arithmetic and re-scanning only for > 19 digits brought it to 12 ns.
- **wasm size** (opt-level z, LTO, stripped, scratch cdylib exporting all functions): the
  whole module is ~20 KB code + 1.3 KB data; `to_string` alone ~4.4 KB. The u16
  instantiation of the generic parsers costs ~3.7 KB (the rare digit-rereading paths take a
  `dyn Iterator` to keep it down).

## Follow-ups
- JSON.parse: JSON's number grammar is a subset of StringNumericLiteral, so the JSON parser can
  validate a number token itself and pass the slice to `string_to_number` (or we add a
  lower-level entry that skips the re-scan if profiles say so).
- If number parsing shows up in JSON benchmarks: 8-digit SWAR scanning for `&[u8]` (std is
  ~2x faster on 17-digit inputs).
- If wasm size matters more: the u16 parsers could convert an ASCII-only trimmed input to u8
  and drop the second instantiation (~3.7 KB).
- console.log prints `-0` for negative zero (qjs' JS_DTOA_MINUS_ZERO); `to_string` returns
  `"0"` as the spec requires, the printer checks the sign itself.
- BigInt <-> string conversion is not covered here.

## Result
`djs_core::num` (crates/djs-core/src/num/), no dependencies, no allocation, no unsafe:

- Formatting: `to_string(x)`, `to_string_radix(x, radix)`, `to_fixed(x, digits)`,
  `to_exponential(x, Option<digits>)`, `to_precision(x, Option<precision>)`. They return
  `NumStr<N>` (stack buffer; `as_bytes()`, `as_str()`, `Deref<Target = str>`), with
  `MAX_SHORT_LEN` (25), `MAX_FIXED_LEN` (123), `MAX_RADIX_LEN` (1077). Arguments are the
  caller's ToIntegerOrInfinity results saturated to i32 (`None` = undefined); range errors come
  back as `RangeError::{Digits, Radix}` with `message()` giving the qjs text.
- Parsing (generic over `CodeUnit` = `u8` Latin-1 / `u16` UTF-16): `string_to_number(s)`
  (Number(str)), `parse_float(s)`, `parse_int(s, radix)` (radix = ToInt32 result),
  `literal_value(bytes)` for lexer-validated numeric literals with `_` separators (decimal,
  0x, 0o, 0b; legacy octal is not handled since strict code rejects it).
- Output matches qjs on the checked-in corpus and 2.1M further random cases. Known
  intentional difference: decimal input with more than 38 significant digits is correctly
  rounded where qjs truncates (D1041).
- Regenerate the corpus with `tests/data/num/gen-corpus.sh`; benchmark with
  `cargo test -p djs-core --release bench_conversions -- --ignored --nocapture`.
