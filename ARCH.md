# djs: Architecture Proposal

Status: initial proposal, meant to be argued with.

djs is a small JavaScript + TypeScript interpreter written in `no_std` Rust (with `alloc`).
It is primarily meant to be compiled to WebAssembly and hosted from JavaScript (pi's
codemode), replacing QuickJS / dquickts there. Behavior should roughly match
`~/Development/dquickts`, which is also the test oracle.

## Goals

In priority order. Each design decision below should be traceable to one of these.

- **G1. Cheap data passing** between the sandbox and the host JS. Tool results (often large
  strings, arrays of similar objects, base64 images) go in, and text, JSON and images come out.
- **G2. Fast startup, compilation and execution as a wasm build.** A codemode script should go
  from source text to running in well under a millisecond plus its own runtime. The wasm
  binary should be small.
- **G3. No AST.** A single-pass compiler goes from tokens to bytecode, like QuickJS.
- **G4. Snapshots** of the whole VM state (heap, stacks, pending jobs, pending host calls), and
  incremental snapshots against a base.
- **G5. Suspend anywhere.** Execution can stop between any two bytecode instructions,
  including inside getters, `toString` calls, `Array.prototype.map` callbacks, promise jobs,
  generators and async functions. The suspended state can then be snapshotted and resumed in
  another process.

Non-goals for now: Intl, Temporal, `SharedArrayBuffer`/Atomics, workers, sloppy mode,
`with`, direct `eval`, a JIT, and full test262 conformance for its own sake.

## The Core Idea

**All VM state lives in one self-managed, position-independent heap: a single contiguous
byte arena addressed by `u32` offsets.**

That covers objects, strings, shapes and property tables, bytecode, function templates, the
JS value stack, call frames, the job queue, the pending host call table, atoms, and realm
intrinsics. Rust data structures (`Vec`, `Box`, `BTreeMap`, …) hold only transient state:
the compiler's working state, and scratch space inside a single native operation.

Each goal follows from this:

- **G4:** a snapshot is a compacting GC followed by a copy of the arena bytes and a small
  header. There is no per-object serializer to write or keep in sync.
- **G5:** the interpreter never recurses on the Rust stack for JS calls. Every frame is in
  the arena, so returning from `run()` at any instruction boundary leaves a complete,
  resumable state.
- **G1:** the host can read sandbox values (especially strings) straight out of wasm linear
  memory without a serialization step, because the heap layout is a documented format.
- **G2:** builtins and the realm are set up once at build time and shipped as a base
  snapshot. Creating a VM means copying that snapshot into a fresh arena. Builtins written
  in JS are precompiled into it, so we pay no compile cost for them at runtime.

Native code is never referenced by pointer from the heap. Native builtins are stored as `u16`
indices into a static table, and host functions as host-assigned `u32` ids. This is what
makes the heap position independent and snapshots possible. It works the same way as
dquickts' native registry, but by construction instead of by fixup.

Accessing the heap through bounds-checked offsets also hardens the sandbox: a VM bug or a
corrupted snapshot can corrupt the JS heap or cause a panic (a wasm trap), but it cannot
cause Rust UB. Unchecked access can be added later as an optimization behind a feature flag.

### Relationship to piccolo

[piccolo](https://github.com/kyren/piccolo) is the model for the **execution side**: a
stackless trampolined interpreter, fuel, and host callbacks that the executor polls instead
of calling recursively. We do **not** adopt its **memory side** (`gc-arena`). There, `Gc`
values are real pointers to Rust-typed allocations, which works against G1 (the host cannot
read the heap) and G4 (snapshots need a full graph serializer). We trade some type safety
for an arena whose bytes are the state.

## Crate / Repo Layout

```
                    intrinsics, snapshot. No platform dependencies.
                    src/builtins/gen/ holds checked-in Rust generated by djs-bgen.
    djs-bgen/       build-time builtin compiler (std, may use an AST and dependencies such as
                    oxc_parser). Checks the builtin TS subset and emits Rust state machines
                    for @native functions and plain JS for everything else.
    djs-prelude/    build.rs compiles bgen's JS output with djs-core and emits the base
                    snapshot (include_bytes!).
    djs-wasm/       wasm32-unknown-unknown cdylib: thin export layer, allocator, panic hook.
    djs-cli/        std binary: run files, REPL, difftest runner, benchmarks.
  builtins/         builtin sources in the strict TS subset (*.ts), intrinsics.d.ts,
                    tsconfig.json (so tsc and editors type-check them).
  js/               TypeScript host package: loads the wasm, wire codec, Sandbox API.
  tests/
    corpus/         differential test cases (js/ts + expected output from dquickts)
    harness/        runner scripts

```

The generated Rust is checked in so that it is reviewable in diffs and the normal build
does not depend on the builtin compiler. `scripts/bgen.sh` regenerates it, and the gate checks
that it is up to date.

Dependencies should stay near zero to keep the wasm small and compile times short. Likely
candidates are `libm` (math) and possibly a small allocator for wasm (`talc` or
`dlmalloc`). We write our own: number formatting (shortest round-trip, Ryu-style),
float parsing (Eisel-Lemire with a fallback), regex, and hashing.

## Values

Values are 64-bit and NaN-boxed:

- Any non-NaN-boxed bit pattern is an `f64`.
- Tagged values: `undefined`, `null`, `bool`, `int32` (optional fast path, can come later),
  the empty/hole marker, and references (string, object, symbol, bigint later, host-ref).
  A reference is a `u32` arena offset.

A `u32` offset is enough on wasm32. If arenas larger than 4 GiB ever matter, offsets can be
scaled by the 8-byte alignment.

## Heap

- **Layout:** each cell starts with a header word (cell kind, GC bits, size). Object cells
  hold a prototype ref, a property storage ref and an elements ref. Strings are separate
  cells.
- **Strings:** JS semantics are WTF-16 (UTF-16 code units, lone surrogates allowed).
  Strings are stored like V8 stores them: **one-byte (Latin-1)** or **two-byte (UTF-16LE)**,
  plus **ropes** for concatenation (codemode builds output with `+=` a lot). Ropes are
  flattened lazily. Atoms (interned strings used as property keys) live in a heap hash table.
- **Objects:** start simple, with a small inline property list (atom → slot, plus flags)
  that switches to a heap hash table above N entries. Shapes / hidden classes come later,
  when benchmarks justify them. Arrays get a dense elements fast path.
- **Code:** function templates (bytecode, constants, line table, scope info) are heap cells.
  That way compiled code is part of snapshots and can be cached as a snapshot.
- **GC:** start with a **copying (Cheney) collector**. It compacts for free, which snapshots
  want; it is simple; and it fits offset-based references. It runs only at safepoints (an
  instruction boundary or an allocation inside a native op where all live values are in
  registered roots). Large strings and buffers (for example a 1 MiB tool output) go into a
  non-moving large-object space later, so they are not copied on every collection. A memory
  cap is enforced on arena growth.
- **Roots:** the realm, the value stack and frames, the job queue, the pending host call
  table, and a host handle table (values the embedder holds). Every root lives in the arena.

Because the arena may grow (and so reallocate), the host must never cache raw pointers
across VM calls. The JS side re-derives its typed-array views after every call, which is
standard wasm practice anyway.

## Compiler (no AST)

The compiler is a recursive-descent parser that emits bytecode directly as it parses, the
way QuickJS does. This needs four techniques:

1. **Token-level lookahead scanning** for ambiguous constructs:
   - An arrow function head `(a, {b}) =>` versus a parenthesized expression: skip the
     balanced parens at token level and check for `=>`.
   - A destructuring assignment `[a, b] = x` / `({a} = x)` versus a literal.
   - TS generic calls `f<T>(x)` versus comparisons: speculatively skip a type argument list
     and check what follows, using tsc's rules.

   The scan only moves the lexer; nothing is emitted.
2. **Rewind:** speculation never emits bytecode. A checkpoint is just the lexer state plus
   the current token, so rewinding is a copy (D1080). The only rewrite of emitted code is
   turning the last instruction (a load) into an assignment target.
3. **Deferred variable resolution:** the compiler emits scope-generic opcodes
   (`get_name atom, scope`) and runs a **resolution pass** once per compilation unit after
   parsing, over all functions, children before parents (D1081). Resolving when a function
   ends is not enough because of hoisting. By then every inner function has reported which
   outer bindings it captures. The pass rewrites each access into a local slot, a
   captured cell (box), or a global lookup. Instructions are encoded so this can be done in
   place, or with one linear re-emit. Hoisting (`var`, function declarations) and TDZ checks
   are handled in the same pass.
4. **Label / jump fixups** are patched when a block closes.

The compiler itself recurses on the Rust stack. That is acceptable because compilation is
bounded by input size and is not something we need to suspend. A nesting-depth limit turns
pathological input into a SyntaxError instead of a stack overflow.

**TypeScript** is erased during parsing. A *type skipper* consumes type annotations, type
parameter and argument lists, `as`/`satisfies`, `!`, `interface`, `type`, `declare`,
overload signatures, and `import type`. Constructs with runtime meaning (enums, namespaces,
parameter properties, later decorators) compile directly to bytecode. Semantics follow tsc
with `isolatedModules` and `useDefineForClassFields`, matching dquickts. There is no
separate TS mode in the core: the flag only enables the TS grammar.

The **bytecode** is stack based, with variable-length instructions (a `u8` opcode and
immediates). Superinstructions come later. A stack VM is the natural target for a
single-pass compiler. A register VM would need either an AST or a much smarter single-pass
allocator.

**Semantics stance:** always strict. Codemode scripts compile as the body of an async
function. A Script mode (global `var`/function bindings on the global object, a global
lexical scope) exists as well, for test262 and `$262.evalScript` (decision D004). Modules
come later and only if needed. There is no direct `eval`; indirect
eval and `Function` may come later.

## Interpreter

```
loop {
    if fuel == 0 { return Status::OutOfFuel }
    decode op at pc; execute; fuel -= cost(op)
}
```

- **Stackless:** a JS → JS call pushes a frame record onto the arena's value stack and
  continues the loop. Returning pops it. The Rust stack depth stays constant.
- **Re-entrant operations without recursion:** an opcode that may invoke user code (getter,
  setter, `valueOf`/`toString` during `+`, iterator protocol in `for-of` / spread /
  destructuring, `instanceof` with `Symbol.hasInstance`, Proxy traps later) pushes a frame
  for the callee with one of a few fixed *continuations* (push the result, discard it,
  the construct result rule, return from `run`). **An op never resumes mid-way** (D1085):
  it runs its fast path inline, and when user code is needed it either calls the user
  function directly (getters, setters) or calls a privileged JS builtin (`%Add`,
  `%ToPropertyKey`, `%GetIterator`, …) that holds the multi-step logic. Nothing is left on
  the Rust stack, and the interpreter has no per-op state machines. (Generated `@native`
  builtins do have states; see "Builtins".)
- **Exceptions:** per-function handler tables map pc ranges to handlers. `finally` uses
  `gosub`/`ret` at a fixed stack depth (D1084). Unwinding walks frames in the arena.
- **Generators and async functions:** on `yield`/`await`, the frame's slice of the value
  stack is copied into a heap generator/async object. Resuming copies it back. Closures
  capture boxed cells, chosen by the resolution pass, so frames never need to outlive
  their stack slot.
- **Promises and jobs:** the microtask queue is a heap structure. Running a job means
  pushing a frame.
- **Fuel:** a counter decremented per instruction, weighted by cost. Native ops charge fuel
  in proportion to the work they do (bytes copied, elements visited). Running out of fuel
  is just another suspension. The embedder turns it into a timeout, a time slice, or a
  snapshot point.

### Builtins

#### The leaf rule

The rule that makes G5 hold for builtins:

> **Hand-written Rust never calls back into JS.** Hand-written Rust is limited to *leaf
> intrinsics* (`%ArrayPush`, `%StringIndexOf`, `%ToPropertyKeyFast`, …), which never run
> user code. Every builtin that may run user code is written in the **builtin language**
> (below) and runs either as bytecode or as a generated, resumable Rust state machine.

- Builtins that may run user code: `Array.prototype.{map,filter,forEach,reduce,find,some,
  every,sort,…}`, `Promise` combinators, `JSON.stringify` with replacer, `toJSON` or
  accessors, `JSON.parse` with reviver, `String.prototype.replace` with a function,
  iterator helpers, `Array.from`, `Object.fromEntries`, and so on. Almost any builtin that
  takes an object qualifies, because `ToPrimitive`, getters and (later) proxies can run
  user code.
- Leaf fast paths stay leaf. A leaf `JSON.stringify` handles the common case (plain data
  objects with no accessors, no `toJSON`, no proxies) and returns a "needs slow path"
  signal that falls back to the full version. `Array.prototype.sort` on primitives without
  a comparator can be a leaf.
- Long leaf ops (for example a regex scan, `JSON.parse` of 10 MB, a big `join`) are
  bounded and fuel-charged. If they turn out to cause suspension latency problems, they
  get an explicit resumable state stored in the heap, as the regex engine has from the
  start (see below).

#### The builtin language

Builtins are written in a **strict subset of TypeScript**, in the spirit of V8's Torque.
One source has two backends:

1. **Bytecode backend (default).** djs-bgen erases types and emits plain JS with
   `%Intrinsic` calls. djs compiles it in privileged mode into the base snapshot. Privileged
   mode unlocks intrinsic calls and opcodes that user code cannot reach (unchecked element
   access, int32 loop counters, direct slot access). This costs nothing in wasm size.
2. **Rust backend (opt-in, `/** @native */`).** djs-bgen emits a resumable Rust state
   machine. It is used for hot paths (`map`, `forEach`, `join`, `indexOf`, the
   `JSON.stringify` slow path, …) and justified by benchmarks, since each one adds wasm size.

Because both backends compile the same source, they can be tested against each other: the
suspension stress mode runs every corpus case with each backend.

The subset:

- Explicit types: `Value`, `Obj`, `Str`, `Sym`, `Fn`, and the numeric types `i32`, `u32`,
  `f64` (branded `number` types in `intrinsics.d.ts`; tsc catches mixing `i32` and `u32`, and
  bgen is the authority on the full numeric rules, D1171). Numeric semantics must agree
  between the backends. Integer arithmetic is checked, and bgen rejects operations whose
  JS and Rust meanings differ.
- Intrinsics are declared in `intrinsics.d.ts` and tagged either `@leaf` (a plain Rust call
  that may throw but never runs JS) or `@reentrant` (may run user code). A call to a
  reentrant intrinsic, a user function or another reentrant builtin is a **resume point**.
  bgen infers these points; the generated Rust marks each one with a comment.
- Abrupt completions map to `Result` in Rust (the spec's `?`). `throw` and `try`/`catch`/
  `finally` are supported, with the handlers recorded in a per-function table.
- Not supported: closures over mutable locals, `arguments`, `eval`, dynamic property
  tricks on builtin locals, and generators (iterator builtins are written as explicit state
  objects). The goal is spec-algorithm style code, nothing more.

Intrinsics themselves (leaf ones) stay hand-written Rust over the heap accessors.

#### Generated state machines

A `@native` builtin runs in a **native frame** in the arena, next to JS frames. The frame
record holds `(native_fn_index, state, locals…)`. bgen knows every local and its type, so
it lays them out as slots. Every reference-typed local lives in a frame slot, which makes
it a GC root. Because the frame holds no pointers, native frames suspend, snapshot and
restore like JS frames.

The GC and fuel rules that keep this simple:

- **No GC inside a state arm.** Allocation never collects. It bumps (growing the arena if
  needed) and sets a `gc_pending` flag. Collection happens only at state transitions and at
  interpreter safepoints. Inside one arm, Rust locals holding references are therefore safe;
  across arms, only frame slots survive.
- **Fuel is charged per transition** (and in proportion to the work leaf calls do). A loop
  back-edge is a transition, so a `map` over a million elements can run out of fuel and
  suspend in the middle, like bytecode would.
- **Fast paths are tried inline, and the slow path is a resume point.** For example `get`
  first tries a leaf lookup of an own data property. Only when it finds a getter (or a
  proxy) does the frame save its state and push the callee. The common case never leaves
  the arm.

Source:

```ts
/** @native */
export function map(this: Value, callback: Value, thisArg: Value): Obj {
  const o: Obj = toObject(this);
  const len: u32 = lengthOfArrayLike(o);       // reentrant: getter, valueOf
  if (!isCallable(callback)) throw typeError("not a function");
  const a: Obj = arraySpeciesCreate(o, len);   // reentrant: constructor, species
  for (let k: u32 = 0; k < len; k++) {
    if (hasProperty(o, k)) {                   // reentrant: proxy trap (later)
      const v: Value = get(o, k);              // reentrant: getter
      createDataProperty(a, k, call(callback, thisArg, v, k, o));
    }
  }
  return a;
}
```

Generated Rust (shape only, slow-path states abbreviated):

```rust
// Generated by djs-bgen from builtins/array.ts:12 (Array.prototype.map). Do not edit.
pub(crate) fn array_map(vm: &mut Vm, fr: NativeFrame) -> Step {
    loop {
        match fr.state(vm) {
            S0 => {
                let o = intr::to_object(vm, fr.this(vm))?;
                fr.set(vm, O, o);
                // resume point: lengthOfArrayLike(o)
                return fr.call_builtin(vm, S1, LENGTH_OF_ARRAY_LIKE, &[o.into()]);
            }
            S1 => {
                fr.set_u32(vm, LEN, fr.result(vm).as_u32());
                if !intr::is_callable(vm, fr.arg(vm, 0)) {
                    return fr.throw(vm, intr::type_error(vm, "not a function"));
                }
                // resume point: arraySpeciesCreate(o, len)
                return fr.call_builtin(vm, S2, ARRAY_SPECIES_CREATE, &[...]);
            }
            S2 => {
                fr.set(vm, A, fr.result(vm));
                fr.set_u32(vm, K, 0);
                fr.goto(vm, LOOP)?; // transition: fuel + gc safepoint
            }
            LOOP => {
                let k = fr.get_u32(vm, K);
                if k >= fr.get_u32(vm, LEN) {
                    return fr.ret(vm, fr.get(vm, A));
                }
                let o = fr.get(vm, O);
                match intr::get_own_fast(vm, o, k) {
                    Fast::Value(v) => {
                        fr.set(vm, V, v);
                        // resume point: call(callback, thisArg, v, k, o)
                        return fr.call(vm, S_STORE, fr.arg(vm, 0), fr.arg(vm, 1),
                                       &[v, k.into(), o.into()]);
                    }
                    Fast::Absent => { fr.set_u32(vm, K, k + 1); fr.goto(vm, LOOP)?; }
                    Fast::Slow => return fr.call_builtin(vm, S_HAS, HAS_PROPERTY, ...),
                }
            }
            S_STORE => {
                let r = fr.result(vm);
                intr::create_data_property(vm, fr.get(vm, A), fr.get_u32(vm, K), r)?;
                fr.set_u32(vm, K, fr.get_u32(vm, K) + 1);
                fr.goto(vm, LOOP)?;
            }
            // S_HAS, S_GET: the hasProperty / get slow path
            _ => unreachable!(),
        }
    }
}
```

`fr.call*` and `fr.ret` return a `Step` to the interpreter loop. The loop pushes the callee
frame (JS or native) and later re-enters `array_map` at the saved state. `?` on a throw
unwinds through the frame's handler table. `fr.goto` returns early (with the state already
saved) when fuel is exhausted or a GC is pending.

On the bytecode backend the same source compiles to ordinary JS frames. A reentrant call
there is just a call, and suspension works as it does for user code.

The **regex** engine is our own backtracking engine. It compiles to regex bytecode stored
in the heap, and its backtrack stack is in the arena. It is fuel-metered and resumable, so
catastrophic backtracking is a timeout, not a hang.

## Host Interface

### Execution API (wasm exports, roughly)

```
vm_new(base_snapshot?) -> vm
vm_compile(vm, src, flags) -> fn | error        // flags: ts, async-body
vm_call(vm, fn, args)                           // pushes a frame, does not run it
vm_run(vm, fuel) -> Status
vm_resolve_host_call(vm, call_id, ok|err, value)
vm_snapshot(vm, base?) -> bytes                 // full or delta
vm_restore(bytes, base?) -> vm
```

```
Status = Done(value) | Threw(value) | OutOfFuel
       | HostCall(call_id, fn_id, args)    // a sync host function was called; frame parked
       | Idle                              // no runnable jobs; waiting on pending host promises
```

- **Async host functions** (`tools.*`, `models.*`): calling one creates a promise and an
  entry `{call_id, fn_id, args, promise}` in the heap's pending host call table. Execution
  continues, and the host reads all new pending calls whenever `run` returns. Resolving one
  enqueues the reaction jobs.
- **Sync host functions** (`text()`, `console.log`, `store`/`load`): the VM returns
  `HostCall` with the frame parked mid-instruction. The host handles it (possibly
  asynchronously on its side), resolves it, and calls `run` again. This is dquickts'
  `JS_SuspendCall` in stackless form, and it means every host call is a suspension point.
- **Durability:** pending host calls are heap state, so they are part of snapshots. After a
  restore, the host decides whether to re-issue them or replay journaled results. The VM
  provides the call ids and arguments.
- **Nondeterminism** (`Math.random` seed, `Date.now`, `performance.now`) comes from host
  imports or heap state, so restores and replays can control it.

### Data passing (G1)

Hot paths in codemode, in order: tool results coming in (strings, sometimes MiBs), text and
console output going out (strings), and structured values both ways (JSON-like; arrays of
similarly shaped objects; base64 images).

- **Outbound, direct read:** the host gets a value handle and reads it with a JS-side
  decoder that understands the heap layout. Strings are decoded in place from linear
  memory: `TextDecoder('utf-16le')` for two-byte strings, a chunked
  `String.fromCharCode` for Latin-1. Note that `TextDecoder('latin1')` is really
  windows-1252 and must not be used. Ropes are flattened first. Objects and arrays are
  walked directly. The VM does no serialization at all.
- **Inbound, wire format:** the host encodes a value into a staging buffer in linear memory,
  and the VM materializes it in one native pass. The format is a compact tagged binary
  encoding (primitives, strings as UTF-8 written with `TextEncoder.encodeInto`, arrays,
  objects with a **key table** so repeated keys are interned once, `Uint8Array`, and
  host refs). The VM transcodes UTF-8 to Latin-1 or UTF-16 natively, which is fast in wasm.
  A lone surrogate cannot survive `encodeInto`; strings that contain one take a UTF-16 path.
- **Baseline to beat:** `JSON.stringify` on the host plus native `JSON.parse` in the VM.
  V8's JSON is very fast, so the binary format has to win in benchmarks to justify itself.
  The wire interface is defined so the encoding can be swapped.
- **Host refs (later):** opaque handles to host objects, for pass-through data such as image
  blocks that the script only forwards to `image()`. They avoid copying entirely. In
  snapshots a host ref is written as an id; the host persists the referenced objects or
  accepts that they are dead after a restore.

### Snapshots (G4)

- **Format:** a header (magic, format version, build hash of the opcode table + native
  table + layout constants, arena length, root offsets) followed by the arena bytes after a
  compacting GC. Everything is little-endian, which matches wasm and the usual native
  targets. A snapshot loads only into the same build, like dquickts.
- **Base snapshot:** the initialized realm and precompiled self-hosted builtins. It is
  produced at build time and embedded in the wasm (or shipped beside it). `vm_new` copies it
  into the arena. That copy *is* startup.
- **Deltas:** split the arena into fixed pages (for example 4 KiB). A delta stores the pages
  that differ from the base, with an optional byte-range patch inside each page. A copying GC
  moves everything, which destroys page stability. So once a base is attached, the
  base-derived region is treated as an **old generation**: it is not moved, and it is only
  collected on a full snapshot. New allocations go after it. That makes deltas small for
  the typical "big prelude + small user state" case.
- **Restore:** validate the header, copy the bytes, re-bind host functions by id and native
  builtins by index. There are no fixups because there are no pointers.

## Performance Budget (initial targets, to be measured)

| Metric | Target |
| --- | --- |
| wasm size (release, `opt-level=z` or `s`, after `wasm-opt`) | < 400 KB (quickjs.wasm is ~850 KB) |
| `vm_new` from the base snapshot | < 100 µs |
| compile throughput | > 50 MB/s of source on native builds |
| interpreter speed | within 1.5x of QuickJS-wasm on microbenchmarks (stretch: parity) |
| host string out, 1 MiB | ~memcpy speed |

The wasm `Module` is compiled once by the host and cached. Each script gets a fresh instance
or a reset arena.

## Hill-Climbing Strategy

We use **differential testing against dquickts** as the oracle. Run every case through
`qjs` (strict mode, async body wrapper) and through djs, then compare stdout, the thrown
error type and message, and the return value.

Corpus, in order of importance:

1. **Real codemode scripts** harvested from pi session logs, with recorded tool results
   replayed through a fake `tools` object. This is the distribution we actually care about.
2. dquickts' `tests/test_language.js`, `test_builtin.js`, `test_typescript.ts` and
   `test_closure.js`, split into individual cases.
3. A test262 subset filtered by feature flags (no Intl, Temporal, `with`, sloppy mode, …).
   It is a long-tail score, not a target in its own right.
4. Generated cases (grammar-based fuzzing) once the basics are stable, also run against the
   oracle.

The loop:

- `djs-cli difftest` prints a pass-rate table per corpus and groups failures by error
  signature.
- Results are recorded per commit (`tests/scores.txt`). **No regressions** is the merge
  gate.
- Each iteration picks the largest failure cluster, fixes it, and re-runs.
- Separate tracks hill-climb on benchmarks: compile time, startup, run time, wasm size,
  data passing. Each has its own tracked numbers.

The **suspension stress mode** (borrowed from dquickts) runs the whole corpus while suspending
every N instructions, snapshotting, restoring into a fresh VM, and resuming. Output must be
identical. This turns G4 and G5 from claims into tested properties from day one.

## Phases

- **P0, skeleton:** workspace, arena + value repr, lexer, compiler for expressions and
  statements, interpreter loop with fuel, `console.log` as a sync host call, difftest
  harness, and suspension stress mode (trivial at this point, and that is the point).
- **P1, core language:** functions, closures and the resolution pass, objects, arrays,
  control flow, exceptions, `let`/`const`/TDZ, template literals, destructuring, spread,
  arrow functions, classes. Copying GC. A minimal privileged compiler mode (`%Name(…)`
  intrinsic calls) and a hand-written `prelude.js` for slow paths (ToPrimitive and the
  like), which bgen replaces in P2 (docs/compiler.md 7.3).
- **P2, codemode MVP:** promises, async/await, job queue, async host functions, djs-bgen
  (subset checker + JS emitter only), builtins in the builtin language on the bytecode
  backend + base snapshot, JSON, core String/Array/Object/Math builtins, the wasm
  build, and the JS host package (wire in, direct read out). **Exit:** pi codemode runs on
  djs behind a flag.
- **P3, TypeScript:** the type skipper, enums, namespaces, parameter properties.
- **P4, durability:** snapshot/restore exposed in the host API, deltas, old generation.
- **P5, long tail:** regex, generators, Map/Set/WeakMap, Symbol, iterators, typed arrays,
  getters/setters edge cases, error stack traces, and whatever the corpus says next.
- **Performance track (parallel from P2 on):** the djs-bgen Rust backend, then moving hot
  builtins to `@native` one at a time as benchmarks justify it.
- Then: shapes / inline caches, int32 fast paths, superinstructions, host refs, decorators,
  `using`.

## Open Questions / Risks

- **Single-pass + TS ambiguities.** Arrow functions, generics and destructuring need careful
  lookahead. QuickJS shows it is feasible for JS; TS adds `<`-ambiguities. Mitigation:
  checkpoint/rewind, plus heavy coverage from `test_typescript.ts`.
- **Self-hosting cost.** Bytecode-backend `map`/`forEach` are slower than native ones unless
  the interpreter is decent. The Rust backend is the answer, but it is a compiler project of
  its own, so it starts only after the bytecode backend has proven the subset.
- **Builtin language scope creep.** The subset must stay small enough that both backends
  are easy to keep correct. Anything that is awkward to express should become a leaf
  intrinsic, not a language feature.
- **Backend divergence.** Numeric semantics, evaluation order and exception unwinding have
  to agree exactly between the two backends. Running the corpus on both is the check.
- **Copying GC with large strings.** Copying collection needs a large-object space early,
  given tool outputs of several MiB.
- **Hand-rolled heap ergonomics.** Typed accessors over byte offsets are less pleasant than
  Rust structs. We should generate the accessors from a single layout description (macro),
  and the JS-side reader should be generated from the same description so the two never
  drift apart.
- **Delta snapshots versus a moving GC.** The old-generation scheme above is a guess; it
  needs measuring against real codemode sessions.
- **Strictness of matching qjs.** Error message texts are part of the oracle comparison.
  Decide early whether we match QuickJS messages verbatim (useful for diffs, since models
  read them) or normalize them in the harness.
